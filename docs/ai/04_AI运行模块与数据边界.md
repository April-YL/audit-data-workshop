# AI运行模块与数据边界

版本：0.1.0；日期：2026-10-30；状态：运行设计已明确，尚未接入模型或产品界面。

## 一、目标与当前状态

AI入口面向通用数据处理。用户可以先用自然语言说明背景和当前需求，再逐步补充条件；系统结合获准使用的数据结构、统计信息和知识包，提出修改建议，并形成可复用的参数化处理方案。

截至本版，项目已有四部分知识包：专业知识及来源、业务本体、资料与系统适配、通用方法。现有产品代码没有模型客户端、模型服务配置、API密钥管理、知识检索服务、多轮会话状态或AI建议界面。知识包尚未参与运行时建议供给，方法的`execution_status`仍为`unbound`。

因此，本文件描述目标结构和边界，不代表相关模块已经实现，也不把知识方案等同于可执行画布。

## 二、运行模块结构

AI建议链由六个模块组成，按下列顺序协作：

1. **本地上下文构建器**：读取用户明确选择的资料，优先在本地提取结构、类型候选、粒度和必要统计；决定哪些内容可以进入模型上下文。
2. **知识加载器**：根据目标、字段语义、资料类型、适用框架和期间，从知识包按引用选择相关概念、方法及专业依据，不把全部知识一次性送入模型。
3. **模型建议接口**：向后续选定的模型服务发送结构化上下文，要求返回符合约定格式的建议草稿；模型不直接访问任意本地文件，也不直接执行SQL、代码或画布节点。
4. **多轮任务状态**：保存已确认事实、未决问题、当前方案、用户新增要求及版本，使用户可以边做边补充需求，而不必一次说完整条处理链。
5. **建议校验器**：在本地检查字段是否存在、类型是否兼容、关键参数是否缺失、关联键是否可能重复以及方法能力是否已经绑定；无法验证的内容标为假设或待确认。
6. **工具绑定与画布应用**：未来将已验证的方法步骤映射到真实节点、参数、端口和支持范围。当前工具尚未全部具备时，只能输出知识方案或部分可实现步骤，不得宣称整条流程可直接运行。

运行关系如下：

`用户输入 → 本地上下文 → 知识筛选 → 模型建议 → 本地校验 → 用户确认 → 未来画布应用`

用户确认不是形式步骤。会改变处理口径、删除或合并记录、修改金额、选择换算依据以及应用专业判断的事项，必须保留明确确认点。

## 三、数据分层与最小外发边界

### 3.1 数据分层

模型所需信息按必要性逐层增加，不以“固定上传前若干行”作为默认办法。

| 层级 | 内容 | 默认位置 | 用途与边界 |
| --- | --- | --- | --- |
| L0 用户描述 | 背景、目标、期望输出、已知限制 | 可进入模型上下文 | 用户可随对话逐步补充 |
| L1 资料结构 | 工作表、物理表头位置、字段名或稳定代号、类型候选、字段顺序 | 本地提取；按任务选取后才可外发 | 用于理解资料形态和匹配方法；字段名也可能敏感 |
| L2 本地统计 | 空值数、不同值数量、类型冲突、键重复、数值范围、日期范围等 | 默认本地计算；仅发送任务必要摘要 | 用较少内容识别风险；统计结果不等于业务含义已确认 |
| L3 代表性样例 | 覆盖常见格式、边界和异常的少量记录 | 默认不外发；用户预览确认后方可使用 | 必须按任务选择和脱敏，不能机械取前N行 |
| L4 原始全量数据 | 完整明细、附件和客户资料 | 仅本地 | Rust与DuckDB处理，不作为通用模型输入 |

默认上下文从L0、必要的L1及L2开始。只有字段结构和统计仍不足以判断格式或语义，而且用户已看到并确认实际发送内容时，才能加入L3。L4不进入通用外部模型服务。

### 3.2 本地保留和禁止外发

以下内容默认保留在本地：

- 原始文件、全量记录及未获准的工作表；
- 本机绝对路径、用户名和目录结构；
- API密钥、访问令牌、连接串和凭据；
- 客户名称、账号、人员身份信息及其他可直接识别主体的信息；
- 与当前任务无关的字段、样例、附件和历史对话数据；
- 本地稳定代号与真实字段或真实主体之间的还原映射。

字段名、统计值、日期范围和金额范围也可能包含敏感信息，不能因为它们不是原始明细就自动视为可外发。上下文构建器应提供“发送前预览”，列出字段、摘要、样例、知识片段和估计范围；模型日志不得记录原始数据或密钥。

模型服务及部署方式尚未选定。在该决定作出前，本文只定义产品侧最小化原则，不承诺任何供应商的数据留存、训练使用、地域或加密条件。

## 四、准确性与证据分级

AI识别准确性不能只依赖用户文字，也不能用模型给出的置信度百分比替代验证。每个事实或建议应标明证据来源：

| 级别 | 证据 | 可支持的结论 |
| --- | --- | --- |
| E1 | 用户明确陈述或确认 | 项目目标、业务口径和选择条件 |
| E2 | 本地读取的结构和物理位置 | 字段存在、顺序、表头及资料形态 |
| E3 | 本地统计和确定性检查 | 空值、重复、类型冲突、范围及候选键风险 |
| E4 | 经用户批准的少量样例 | 格式候选、异常表现和语义线索 |
| E5 | 已筛选知识来源 | 方法建议、适用条件和专业复核要求 |

模型负责解释、提出候选关系和组织方案；本地程序负责可确定验证。至少应检查：字段存在性、数据类型、参数完整性、键的重复与空值、关联基数、处理前后行数和必要控制数。

字段别名只能用于提出映射候选。名称相似、同一系统常见叫法或少量样例均不足以自动确认字段含义。涉及业务粒度、金额口径、期间、币种、单位或保留规则的歧义，应向用户提出最小必要问题。

## 五、效率原则

在保证判断所需证据的前提下，减少上下文和重复处理：

1. 只选择当前目标涉及的资料、字段和知识条目。
2. 统计在本地计算，优先发送结论性摘要而非明细。
3. 样例按格式、边界和异常覆盖选择，不按固定行数机械截取。
4. 已确认事实带版本保存；数据集、字段结构或处理方案未变化时可复用。
5. 用户补充要求时只增加受影响的上下文，并标明哪些旧结论需要重新验证。
6. 为字段数量、统计项目、样例行数和知识片段设置可见预算；超出预算时先说明缺口和影响。

效率优化不得以隐藏发送内容、跳过必要验证或默认补齐业务参数为代价。

## 六、渐进式交互与任务状态

用户可以先描述一部分需求，AI给出当前理解、建议和少量关键问题；后续补充应合并到同一任务，而不是要求重新描述全部背景。

多轮任务状态至少包含：

- `goal`：当前处理目标和期望输出；
- `confirmed_datasets`：用户选定的资料及其结构版本；
- `facts_with_evidence`：已确认事实及E1—E5证据；
- `confirmed_semantics`：已确认字段含义、粒度、单位、期间等；
- `current_plan`：当前方法步骤、参数和依赖关系；
- `pending_suggestions`：尚未接受、拒绝或修改的建议；
- `clarifications`：仍会影响结果的待确认问题；
- `dataset_version`与`workflow_version`：资料或方案变化的版本；
- `invalidated_items`：因新信息失效、需要重算或复核的结论；
- `change_history`：用户确认的新增、修改、撤回及原因。

每轮建议应区分“在现有步骤后追加”“修改现有步骤”“替换一段步骤”和“仅提供解释”。修改既有方案时，应显示受影响的后续步骤、复核项和失效结论。聊天文本不是唯一状态来源，关键事实和参数必须结构化保存。

## 七、建议输出契约

模型输出应先解析为结构化草稿，再由本地校验器检查。建议结构如下：

- `goal`：对当前目标的简洁复述；
- `facts_with_evidence`：事实、证据级别及来源；
- `assumptions`：尚未证实但用于提出候选方案的假设；
- `suggestions_with_reasons`：建议、理由及预计影响；
- `concept_refs`与`source_refs`：实际采用的知识引用；
- `clarifications`：只保留会改变结果的关键问题；
- `steps`：`method_id`、参数、输入、输出和依赖；
- `expected_outputs`：预期数据集、字段或复核结果；
- `exceptions`与`review_requirements`：异常去向和人工复核；
- `reuse_parameters`：可复用时需要重新绑定的参数；
- `unresolved_capabilities`：当前工具不能实现或尚未验证的部分；
- `plan_status`：`needs_clarification`、`blocked_for_basis_confirmation`或`ready_as_knowledge_plan`。

事实、推断和建议必须分开。`ready_as_knowledge_plan`只表示知识层方案完整，不表示已经绑定工具、获得执行授权或通过运行验证。

## 八、分阶段实现顺序

后续实现应逐阶段验收，不直接从知识JSON跳到自动修改画布：

1. 明确模型服务选择、部署方式、认证保存位置、日志和数据保留条件。
2. 实现本地上下文构建器、发送前预览和脱敏代号映射。
3. 实现知识加载器及来源、适用范围和状态筛选。
4. 实现结构化模型接口和建议输出解析，先提供只读建议。
5. 实现多轮任务状态、增量补充、版本和失效管理。
6. 实现本地建议校验，并建立虚构案例、反例和模型评测。
7. 随真实节点成熟，逐项绑定方法能力；先生成可审阅草稿，再经用户确认应用到画布。

在第1项尚未确认前，可以继续完善本地模块契约和测试设计，但不能把任何模型供应商假定为产品既定方案。

## 九、验收边界

本设计的文档验收包括：运行模块职责清楚、数据分层可执行、禁止外发内容明确、渐进式状态可追踪、建议输出可校验、现状与未来能力不混淆。

未来产品验收还需单独覆盖：不同资料结构下的字段识别、最小上下文是否足够、脱敏前后语义保持、知识检索适用性、关键缺口追问、错误建议拦截、多轮修改一致性、日志脱敏和工具绑定。仅能生成一段看似合理的文字，不构成AI能力验收通过。
